# B2-11 — Gateway MQTT e AMQP bidirecional

- **Status:** Concluída
- **Dependências:** [B2-07](B2-07.md), [B2-10](B2-10.md)
- **Frente / prioridade:** Backend / P0
- **Meta original:** 2026-10-21

## Aceite

Ida e volta passam pelos dois brokers, sem conexão MQTT direta da API no fluxo novo.

## Passo a passo

1. Adaptar validação atual para gateway: telemetria e ACK MQTT viram mensagens RabbitMQ.
2. Consumir comandos autorizados de RabbitMQ e publicar em tópico do dispositivo no Mosquitto.
3. Tratar reconexão, confirmação de publicação, duplicatas e erros preservados; evitar loop de republicação.

## Áreas e interfaces afetadas

Gateway Python, MQTT existente e cliente AMQP.

## Como testar

Percurso real de telemetria e comando, broker indisponível, duplicata e mensagem malformada.

## Execução — 14/10/2026

**Resultado:** aceite cumprido no escopo do gateway. Telemetria e ACK saem do
simulador por MQTT, recebem validação/aceite durável no gateway e chegam ao
RabbitMQ. Comandos publicados com identidade AMQP da API atravessam RabbitMQ,
gateway e Mosquitto, alteram LED/buzzer e retornam ACK correlacionado pelo mesmo
gateway. A API não conecta ao MQTT no fluxo novo. API v1/v2 e seus dados conservam
o transporte anterior; não há endpoint HTTP v3 entregue nesta tarefa.

### Aceites comprovados

- [x] MQTT → AMQP real: seis sensores e ACK v3, JSON estrito/8192 bytes/schema/
  FormatChecker, tópico/key/IDs/unidades, QoS 1, sem retain e `received_at` inicial
  imutável. Mensagem RabbitMQ persistente, confirms/mandatory e metadados coerentes.
- [x] AMQP → MQTT real: identidade de serviço API publica somente em RabbitMQ;
  gateway consome `coldsafe.gateway`, valida comando/atuador/escopo/prazo e publica
  somente em commands MQTT. LED/manual e buzzer/automatic alteram telemetria;
  ACK possui comando/atuador/correlação corretos. Nenhum bypass MQTT da API v3.
- [x] PostgreSQL real valida dispositivo ativo, ambiente e proprietário configurado.
  Revogação por `is_active=false` rejeita telemetria; restauração volta a aceitar.
  Equipamento/sensores/atuadores são conferidos no catálogo privado de comissionamento,
  pois ainda não há tabelas/API dessas entidades. IDs recebidos não redefinem vínculos.
- [x] Diário SQLite privado grava antes do ACK MQTT e conserva primeira recepção,
  pendências, erros e comandos entre reinícios. Mesmo ID/corpo é deduplicado;
  conflito de corpo/command_id/event_id, inclusive entre transportes, é recusado.
  Repetir ligar após desligar não republica nem religa; teste observa também MQTT,
  sem depender apenas do cache do simulador para provar a deduplicação do gateway.
- [x] RabbitMQ indisponível: SQLite conserva telemetria e drena após reconexão,
  preservando identidade/aceite. Mosquitto reinicia e restaura telemetria/comandos.
  MQTT indisponível: três tentativas, erro sanitizado por tentativa, original e
  propriedades preservados na DLQ; nenhuma republicação AMQP para zerar o contador.
- [x] MQTT malformado: bytes originais privados no diário, `processing_error`
  sanitizado no bus. AMQP malformado: DLQ preserva original/contexto. Logs sem payload
  ou credenciais; erro sem escopo validado tem identidades/source nulos.
- [x] Confirmação MQTT negativa/ausente não marca entrega nem dá ACK AMQP.
  Com simulador parado, PUBACK não inventa ACK do equipamento. Gateway não produz
  `confirmed`, timeout ou sucesso de negócio a partir de publicação.

### Falhas corrigidas e como testar

1. **Ausência da ponte:** não existia consumidor/produtor v3 entre os brokers.
   Arquivos: `gateway/`, Compose e testes novos. Solução: fronteiras validadas,
   diário e transporte bidirecional com confirmações. Testar pela suíte real acima.
2. **Teste assumia prontidão após start:** Docker iniciar processo não garante
   inscrição MQTT; causa provável da falta do primeiro ACK no caso de duplicata.
   Arquivo: `test_gateway_integration.py`. Solução: Probe novo assina antes do
   start, aguarda nova telemetria e mesmo event_id em RabbitMQ em toda retomada,
   sem sleep fixo. Testar os 11 casos na ordem completa, como na rodada final.
3. **Fixtures de teste:** Mock simples não suporta context manager; contexto
   SQLite não fecha a conexão automaticamente. Arquivos: testes unitários novos.
   Solução: MagicMock e `contextlib.closing`; regressão final sem esses avisos.

### Limites, pendências e checkpoint

Sem pendência dentro do aceite B2-11. Limites explícitos: um dispositivo live
`sim-lab-01`; catálogo comissionado em arquivo para sensores/atuadores/equipamento;
SQL read-only usa parâmetros/credencial PostgreSQL existente, sem provisionar papel
SQL exclusivo. O ensaio de revogação real cobre dispositivo inativo/restaurado,
sem ensaiar transferência de proprietário entre contas.

Diário retém identidades/entrada/saída/erros até aproximadamente 64 MiB e não expurga:
pode encher em poucas horas a 1 Hz. Ao encher, interrompe sem ACK de dados não
gravados. Arquivamento/deduplicação com retenção explícita é necessário antes
de operação prolongada; não apagar volume como forma de reiniciar.
Sessão MQTT tem 24 h e filas limitadas. Não há transação distribuída/exatamente
uma vez entre brokers/SQLite/atuador; queda entre confirmações pode repetir entrega.
O simulador conserva estado/cache em memória; restart perde ambos.

Ausência de ACK com simulador parado foi observada por 1,5 s; não substitui máquina
durável de status/timeout. Autorização HTTP v3, persistência InfluxDB, regras,
entrega Web e demais consumidores continuam posteriores. Não rodou suíte completa
do backend, frontend/E2E, hardware/Wokwi, soak/carga ou capacidade final B2-33.
