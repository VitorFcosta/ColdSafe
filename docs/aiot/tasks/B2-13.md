# B2-13 — Consumidor da API, regras e WebSocket

- **Status:** Concluída
- **Dependências:** [B2-06](B2-06.md), [B2-11](B2-11.md), [B2-12](B2-12.md)
- **Frente / prioridade:** API / P0
- **Meta original:** 2026-10-22 a 2026-10-23

## Aceite

Regras e notificações funcionam via RabbitMQ; WebSocket de uma conta não recebe dados de outra.

## Passo a passo

1. Consumir telemetria/ACK e eventos de persistência/previsão; reaproveitar regras do buzzer e estados pending/confirmed/rejected/unconfirmed.
2. Publicar comando automático pelo RabbitMQ, deduplicando avaliação e auditando efeitos.
3. Entregar eventos completos via WebSocket filtrados por proprietário; REST recupera estado na reconexão e histórico, sem depender da ordem entre consumidores.

## Áreas e interfaces afetadas

API, regras, consumidor de eventos e eventos WebSocket.

## Como testar

Leitura nova antes/depois da gravação, reconexão, ACK tardio e ausência de dados; nenhum bypass MQTT na API.

## Resultado — 15/10/2026

Implementação, aceites específicos e regressão ampla aprovados. Fonte desta entrega: o cartão
e as dependências locais B2-06/11/12, sem replanejamento nem consulta ao Notion.

### Aceites verificados

- [x] API consome filas `commands`/`delivery` com credenciais próprias. JSON estrito,
  schema v3, tamanho, metadados, catálogo e proprietário revalidados; ACK somente
  após transação. Erros sanitizados, até três tentativas e DLQ.
- [x] Avaliação de temperatura ambiente com histerese, comando automático e
  auditoria atômicos com inbox/outbox. Reentrega não repete efeito; restart conserva
  saídas pendentes. LED manual exige operador/admin proprietário.
- [x] `pending/confirmed/rejected/unconfirmed` duráveis, separados dos comandos
  legados. ACK usa primeiro aceite confiável e prazo inclusivo de 30 segundos;
  ACK tardio é auditado e não desfaz timeout persistido.
- [x] Writer produz `telemetry_persisted` após escrita síncrona e antes do ACK.
  Leituras/previsões aguardam vínculo e prova de persistência para entrega WS,
  independentemente da ordem entre consumidores. Previsão antiga não substitui
  a leitura nova, nem renova freshness; histórico conserva envelope original.
- [x] REST v3 recupera estado/histórico processado com `pending/persisted`.
  `no_data` antes da primeira leitura; stale após 30 s, sem recuperação fictícia
  de alerta. Stream v3 separado, ticket de uso único e revalidação de sessão/dono.
  Duas contas reais isoladas em REST, ticket e WebSocket.
- [x] Buzzer automático e LED manual percorreram AMQP → gateway → MQTT →
  simulador → ACK e terminaram confirmados. O fluxo v3 da API não publica MQTT.

### Limitações e checkpoint de retomada

- HTTP/WS da integração usam FastAPI/Starlette `TestClient` real; bancos, brokers,
  writer, gateway e simulador são Docker reais. Backend completo na pilha pessoal,
  hardware físico e frontend v3 não foram executados. Testes usam volumes e
  credenciais descartáveis, removidos ao final; `.env` pessoal preservado.
- Um catálogo/equipamento/dono comissionado por runtime. Cadastro de equipamentos
  e integração do dashboard não fazem parte deste cartão.
- WS admite reentregas: dedup de 1024 IDs em memória, sem replay durável. Cliente
  deve usar `event_id` e REST na reconexão. Inbox/eventos/outbox sem expurgo;
  capacidade/retenção finais pertencem à B2-33. Dados v1/v2 ficam no bucket legado.
- Previsões foram consumidas com exemplos controlados; inferência/modelos reais
  e histerese preditiva pertencem à B2-25/26. Dependência inválida detectada após
  chegada da fonte fica em auditoria `aiot_link_rejected`, sem entrega; mensagem
  já confirmada não é movida retroativamente para DLQ.
- Para operar: mesmo catálogo/dono no gateway, writer e API; importar novas ACLs
  sem apagar volumes; habilitar `compose.aiot.yaml` conforme configuração.
