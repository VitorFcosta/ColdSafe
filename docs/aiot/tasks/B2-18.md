# B2-18 — Gerador massivo em blocos

- **Status:** Concluída
- **Dependências:** [B2-09](B2-09.md), [B2-17](B2-17.md)
- **Frente / prioridade:** Dados / P0
- **Meta original:** 2026-10-27

## Aceite

Dataset reproduzível e não perfeito, com volume verificado e pico de memória documentado; labels só offline.

## Passo a passo

1. Implementar geração NumPy vetorizada em blocos para pelo menos 1 milhão de leituras; teto inicial 2 milhões e gravação em disco.
2. Aplicar parâmetros de quantidade/tipos de sensores, dias, falhas, modos, ruído, faltantes, outliers e seed; incluir ciclo diário e degradação progressiva.
3. Guardar labels de degradação, saúde e tempo até falha somente no dataset; registrar esquema/unidades/seed. Não inventar RUL para vida incompleta: registrar censura e excluir esses alvos da avaliação de RUL.

## Áreas e interfaces afetadas

Worker geração, NumPy e volume de datasets.

## Como testar

Mesma seed reproduz resultados; contagem mínima, ruído/sobreposição, teto, memória e separação do bucket ao vivo.

## Resultado — 16/10/2026

Aceite cumprido no escopo de **geração offline sintética**, integrada ao worker
B2-17. Não é treinamento nem validação física/industrial. Dataset privado é
registrado só depois do manifesto e dos blocos duráveis em disco.

### Aceites comprovados

- [x] NumPy vetorizado em blocos de 50.000; 1.000.000 e 2.000.000 de linhas
  verificadas em disco. API rejeita volumes fora desse intervalo. Uma linha é
  uma observação de equipamento com até seis medições, não uma célula.
- [x] Quantidade de equipamentos/tipos de sensores, dias, modos de operação/falha,
  proporção de falhas observadas, ruído, faltantes, outliers e seed validados e
  aplicados. Quantidade de sensores = equipamentos × tipos selecionados.
  Ciclo diário, baselines/fases distintos e degradação alteram as quatro variáveis
  de desgaste do simulador; heterogeneidade/ruído sobrepõem faixas de saúde.
- [x] Duas execuções novas de 1 milhão, mesma seed/configuração/versão, tiveram
  SHA-256 idêntico em todos os 20 blocos. Outra seed muda as medições.
- [x] Manifesto registra esquema/unidades/configuração/seed/NumPy, equipamentos e
  contagem/hash dos blocos. Linha lógica validada contra `offline_row`; NPY usa
  NaN para faltantes/RUL censurada, convertidos a null na representação JSON.
  `degradation_true` opcional 0–1 acrescentado só ao schema offline, preservando
  linhas anteriores; o novo gerador sempre grava esse label.
- [x] Saúde/degradação/RUL só no dataset offline. Sem falha observada, RUL nula;
  falha observada admite zero. Censurados devem ser excluídos da avaliação de RUL.
  Sem amostras/labels em MQTT/AMQP nem gravação no bucket live; ensaio AMQP real
  confirmou apenas metadados de progresso na saída do worker.
- [x] PostgreSQL real comprovou vínculo dataset/dono/job, isolamento, conclusão
  com artefato, interrupção/retomada, ambiente opcional preservado no manifesto
  e falha de escrita sem dataset registrado.
- [x] Volume Docker persistente, usuário sem root, geração RW e API/treino RO;
  segundo container lê o dataset após restart e montagem RO recusa escrita.

### Volume e pico de memória medidos

Processos novos, Python 3.13.15 / NumPy 2.5.4, seed 42, parâmetros padrão.
RSS é o máximo do processo inteiro via `resource.getrusage`, incluindo validação
dos arquivos; não inclui a soma da pilha nem o cache de disco do kernel.

| Ensaio | Linhas / blocos | Disco | Pico RSS | Tempo |

| macOS A | 1.000.000 / 20 | 85.026.592 bytes | 85.999.616 bytes (82,02 MiB) | 1,269 s |
| macOS B, reprodução | 1.000.000 / 20 | 85.026.592 bytes | 92.323.840 bytes (88,05 MiB) | 0,686 s |
| macOS, teto | 2.000.000 / 40 | 170.038.632 bytes | 93.339.648 bytes (89,02 MiB) | 1,690 s |
| Linux Docker, teto | 2.000.000 / 40 | 170.038.632 bytes | 95.838.208 bytes (91,40 MiB) | 2,092 s |

Docker usou filesystem read-only, volume gravável, rede desabilitada,
512 MiB/1 CPU e sem capabilities. Esse benchmark precedeu o ajuste final do
metadado `environment_id`; fórmulas/NPY não mudaram depois. Imagem final
reconstruída e ajuste exercitado na suíte final. Dataset padrão de 1 milhão:
59.460 medições faltantes e 60 falhas finais observadas; 40 equipamentos censurados.
Isso não promete tempo/memória da pilha B2-33 nem precisão de modelo.

### Limitações, pendências e como testar

Retomada **repete o cálculo todo** em novo diretório, sem reutilizar blocos antigos.
Checkpoint do contador máximo por bloco confere conexão e não regride progresso.
Tentativas interrompidas podem deixar órfãos; limpeza manual com workers parados
e preservação das chaves referenciadas em `datasets.artifact_key`.
Perda da sessão PostgreSQL pode liberar lock antes do próximo checkpoint;
diretório exclusivo evita corrupção, sem exclusão garantida de CPU nessa janela.

IDs/horários são sintéticos; bytes reproduzíveis no mesmo ambiente/versão/configuração,
sem promessa entre plataformas. Fração de falhas é probabilística por equipamento.
Não há calibração industrial. Validação/importação/interface, features e avaliação
de RUL pertencem às próximas tarefas. Nenhuma pendência identificada no aceite B2-18.

Na raiz, usando o lock dev:

```sh
python -m pytest backend/tests/services/test_generation.py --no-cov -o addopts='' -q
python -m scripts.benchmark_generation --output /tmp/coldsafe-b218-repro-1m --total 1000000 --seed 42
```

Diretório de saída precisa ser novo. Para o teto use `--total 2000000`; compare
`block_hashes` dos relatórios de duas execuções para conferir a seed. Integração
requer PostgreSQL descartável via `POSTGRES_TEST_*`; `COLDSAFE_RABBITMQ_INTEGRATION=1`
habilita também o quarto caso, com broker removido no fim. Operação no
[backend](../../../backend/README.md#geração-offline-b2-18).
